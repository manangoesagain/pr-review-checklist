PR Review Checklist: app map

A one-page guide to where things live in this app, so you know where to start when you want to change something. It is a snapshot of the code at the commit named at the bottom, so it can drift as the code changes.

What the app does

You paste a link to a public GitHub pull request (or a diff). The app reads the changed lines, asks an AI for a short checklist in five areas (security, tests, breaking changes, docs, performance), and then checks every item against the real code before showing it. Anything it can't prove is hidden, and the review tells you how many were hidden and why.

  • The pagepublic/app.html, public/app.js, public/styles.css
  • The serverserver.js: one route, POST /api/review, that streams progress
  • The review stepslib/: one small file per step, run in order by lib/review.js
  • The checklist questionsrules/*.json: the questions and code patterns per area

One action, end to end: clicking "Review it"

The route: three stops

A reference route. Open the project folder in your editor and use your editor's search (Ctrl+Shift+F in VS Code) for the names in code.

1

The button. public/app.js, search for function startReview.

Clicking "Review it" (or "Try the example PR") calls startReview. It opens the pop-up, then streamReview sends the link to /api/review and reads the answer one line at a time. Each line is a step ("fetch", "facts", "ai", "verify"), which is why the progress list ticks along live. The last line is the finished review.

What a streamed answer looks like 
{"step":"fetch"}
{"step":"facts"}
{"step":"ai"}
{"step":"verify"}
{"review":{"mode":"ai","areas":[ ... ],"hidden":[ ... ]}}
2

The steps, in order. lib/review.js, search for export async function runReview.

This one function is the whole review. It reads the PR (lib/github.js), counts plain facts such as "no test files changed" (lib/facts.js), finds pattern hints such as SQL built from text (lib/hints.js with rules/*.json), and then asks the AI. If the AI fails for any reason, it still returns the facts and hints as a basic checklist, so you always get something.

The AI's instructions are in lib/prompt.js, function systemPrompt. Every diff line is sent with a label like R15 (new line 15), and the AI must quote the exact line it means.

3

The proof. lib/verify.js, search for export function lineCheck; then lib/claims.js, export async function checkClaims.

lineCheck keeps an AI item only if its file exists in the PR, its line label exists, and its quoted code really is on that line. checkClaims then asks the AI a second, sceptical question about each item ("is this really a problem on this line?") and hides the ones that aren't, including praise dressed up as a problem. Hidden items are listed at the bottom of the review with the reason.

A practice to reuse

Don't trust what an AI says; make it point at proof you can check, and measure it.

In this app the AI must cite a line label and quote the line (lib/prompt.js), the code checks the quote against the real diff (lib/verify.js, lineCheck), and a second sceptical pass catches the rest (lib/claims.js). A fixed test set measured the result: node eval/run-eval.js --runs 3 reviews a demo PR with 5 planted problems and a clean PR with none. Before the praise filter it raised about 3 false alarms per run on the clean PR; after it, 0.3, while still finding 14 of the 15 planted problems (runs on 2026-10-07 and 2026-10-08).

The same idea works in other projects: ask the AI for an answer in a shape your code can check against real data, throw away what doesn't check out, and keep a small fixed test set so you can tell whether a change made things better or worse.

Run it again

  1. Open a terminal in the project folder.
  2. First time only: npm install. Put your NVIDIA key in .env as NVIDIA_API_KEY=... (without it the app still runs, in basic mode).
  3. npm start, then open http://localhost:3000/app. Keep the terminal open while you use it.
  4. Tests: npm test.
